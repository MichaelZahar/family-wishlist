# Feature Specification: F1 · Auth и семья

**Feature Branch**: `001-auth-family`

**Created**: 2026-11-12

**Status**: Draft

**Input**: User description: "docs/briefs/F1-auth-family.md"

Источник: `docs/briefs/F1-auth-family.md` (утверждён 2026-11-12). Правила `R-AUTH-01…10` — `docs/prd.md`, раздел 5.
Обозначение `AC-n` — acceptance criteria брифа.

## User Scenarios & Testing _(mandatory)_

### User Story 1 - Создание семьи (Priority: P1)

Человек без аккаунта регистрируется, указывая email, пароль, имя и название семьи. Он получает семью, взрослый профиль и роль admin и сразу оказывается в приложении.

**Why this priority**: без семьи и admin недоступен ни один другой сценарий продукта.

**Independent Test**: зарегистрироваться на пустой системе и убедиться, что пользователь вошёл как admin новой семьи.

**Acceptance Scenarios**:

1. **Given** нет аккаунта, **When** человек регистрируется с email, паролем, именем и названием семьи, **Then** созданы аккаунт, семья и взрослый профиль; пользователь — admin этой семьи и уже вошёл (AC-1, R-AUTH-01).
2. **Given** форма регистрации, **When** пароль короче 10 символов, **Then** регистрация отклонена с сообщением о минимальной длине; аккаунт и семья не созданы (R-AUTH-10).
3. **Given** форма регистрации, **When** пароль из 10 символов одного вида (только буквы или только цифры), **Then** регистрация проходит (R-AUTH-10).
4. **Given** форма регистрации, **When** не заполнено любое из полей: email, пароль, имя, название семьи, **Then** регистрация отклонена с указанием поля; ничего не создано.
5. **Given** аккаунт с этим email существует, **When** человек регистрируется с ним, **Then** отказ «email уже зарегистрирован»; аккаунт и семья не созданы (FR-035).

---

### User Story 2 - Вход и выход (Priority: P1)

Участник семьи входит по email и паролю, остаётся в системе между визитами и может выйти.

**Why this priority**: без повторного входа аккаунт из User Story 1 одноразовый.

**Independent Test**: войти существующим аккаунтом, открыть защищённую страницу, выйти и убедиться, что страница недоступна.

**Acceptance Scenarios**:

1. **Given** аккаунт существует, **When** пользователь вводит верные email и пароль, **Then** он входит в свою семью (AC-6, R-AUTH-07).
2. **Given** пользователь вошёл, **When** он выходит, **Then** защищённые страницы недоступны и ведут на вход (AC-6).
3. **Given** пользователь вошёл, **When** он возвращается в течение 30 дней после последнего визита, **Then** повторный вход не требуется (R-AUTH-07).
4. **Given** пользователь вошёл, **When** с последнего визита прошло больше 30 дней, **Then** требуется вход (R-AUTH-07).
5. **Given** аккаунт существует, **When** введён неверный пароль или несуществующий email, **Then** отказ с одинаковым сообщением в обоих случаях (AC-7, N-SEC-07).
6. **Given** аккаунт существует, **When** сделано 6 неверных попыток входа за минуту с одного адреса для одного email, **Then** шестая отклонена как превышение лимита; ответ не раскрывает, существует ли email (AC-7, N-SEC-07).
7. **Given** пользователь не вошёл, **When** он открывает защищённую страницу, **Then** он попадает на вход.

---

### User Story 3 - Приглашение взрослого по ссылке (Priority: P2)

admin создаёт приглашение и получает ссылку, которую сам передаёт человеку. Приглашённый открывает ссылку, задаёт email, пароль и имя и становится member семьи с собственным профилем. Неиспользованное приглашение admin может отозвать.

**Why this priority**: семья из одного человека не даёт ценности продукта; сценарий зависит от User Story 1 и 2.

**Independent Test**: admin создаёт приглашение, второй человек регистрируется по ссылке и видит себя участником той же семьи; повторное открытие ссылки даёт отказ.

**Acceptance Scenarios**:

1. **Given** пользователь — admin, **When** он создаёт приглашение, **Then** он получает ссылку, действующую 7 дней и одноразовую (AC-2, R-AUTH-02).
2. **Given** действующая ссылка приглашения, **When** человек открывает её и задаёт email, пароль и имя, **Then** он — member этой семьи с собственным взрослым профилем и уже вошёл; ссылка больше не работает (AC-3, R-AUTH-03).
3. **Given** ссылка истекла, использована или отозвана, **When** человек открывает её, **Then** он видит отказ с подсказкой запросить новое приглашение у admin; аккаунт не создан (AC-4, R-AUTH-04).
4. **Given** admin создал приглашение и оно не использовано, **When** admin отзывает его из списка действующих приглашений, **Then** ссылка перестаёт работать сразу; приглашение исчезает из списка (R-AUTH-06, N-SEC-06, FR-036).
5. **Given** пользователь — member, **When** он пытается создать или отозвать приглашение через интерфейс или напрямую через API, **Then** отказ «нет прав»; приглашение не создано и не отозвано (AC-5, `permissions.md`, «Семья»).
6. **Given** пользователь вошёл и состоит в семье, **When** он открывает ссылку приглашения, **Then** отказ; состав семей не меняется (R-AUTH-05).
7. **Given** действующая ссылка приглашения, **When** пароль короче 10 символов, **Then** регистрация отклонена; приглашение остаётся действующим (R-AUTH-10).
8. **Given** приглашение использовано, **When** admin пытается его отозвать, **Then** отказ; участник остаётся в семье (R-AUTH-06).
9. **Given** пользователь — admin и есть два действующих приглашения, **When** он открывает список приглашений, **Then** он видит оба с датой создания и сроком действия; ссылки не показаны (FR-036, FR-038).
10. **Given** пользователь — member, **When** он запрашивает список приглашений через интерфейс или API, **Then** отказ «нет прав» (FR-037).
11. **Given** действующая ссылка приглашения, **When** человек задаёт email существующего аккаунта, **Then** отказ «email уже зарегистрирован»; аккаунт не создан, приглашение остаётся действующим (FR-035).

### User Story 4 - Сброс пароля через admin (Priority: P3)

Участник забыл пароль. admin выпускает для него ссылку сброса и передаёт её сам. Участник задаёт новый пароль; все его прежние сессии завершаются.

**Why this priority**: восстановление доступа нужно реже, чем вход и приглашения, но без него забытый пароль означает потерю аккаунта.

**Independent Test**: admin выпускает ссылку для участника с активной сессией; участник задаёт новый пароль; старая сессия и старый пароль не работают, новый — работает.

**Acceptance Scenarios**:

1. **Given** пользователь — admin и участник его семьи забыл пароль, **When** admin выпускает ссылку сброса и участник задаёт по ней новый пароль, **Then** участник входит с новым паролем; старый пароль не работает; ссылка больше не работает (AC-8, R-AUTH-08).
2. **Given** у участника есть активные сессии, **When** он задаёт новый пароль по ссылке сброса, **Then** все его прежние сессии завершены (AC-8, R-AUTH-08).
3. **Given** ссылка сброса выпущена больше 24 часов назад, **When** участник открывает её, **Then** отказ с подсказкой запросить новую ссылку у admin; пароль не изменён (R-AUTH-08).
4. **Given** пользователь — member, **When** он пытается выпустить ссылку сброса для другого участника, **Then** отказ «нет прав» (`permissions.md`, «Семья»).
5. **Given** ссылка сброса, **When** новый пароль короче 10 символов, **Then** отказ; ссылка остаётся действующей (R-AUTH-10).
6. **Given** для участника выпущена ссылка сброса, **When** admin выпускает для него новую, **Then** работает только последняя.

### User Story 5 - Профиль: имя и язык (Priority: P3)

Вошедший пользователь меняет своё отображаемое имя и язык интерфейса (`ru` или `en`). Язык сохраняется в профиле и действует на любом устройстве после входа.

**Why this priority**: приложением можно пользоваться с именем из регистрации и языком браузера.

**Independent Test**: сменить язык на `en`, выйти, войти в другом браузере — интерфейс на английском.

**Acceptance Scenarios**:

1. **Given** пользователь вошёл, **When** он меняет язык на `en`, **Then** интерфейс сразу на английском; настройка сохраняется между сессиями и устройствами (AC-10, R-AUTH-09).
2. **Given** пользователь вошёл, **When** он меняет отображаемое имя, **Then** новое имя видно ему и участникам его семьи (R-AUTH-09).
3. **Given** пользователь не вошёл, **When** он открывает приложение, **Then** язык интерфейса — язык браузера, если это `ru` или `en`; иначе `en` (N-UX-04).
4. **Given** человек регистрируется, **When** аккаунт создан, **Then** язык профиля равен языку интерфейса в момент регистрации.
5. **Given** пользователь вошёл, **When** он сохраняет пустое имя, **Then** отказ; имя не изменено.

### User Story 6 - Изоляция семей (Priority: P1)

Участник одной семьи не получает никаких данных другой семьи и не может действовать в ней — ни через интерфейс, ни через прямые запросы к API.

**Why this priority**: утечка между семьями — критический баг (конституция, принцип V; D-01).

**Independent Test**: создать две семьи; под admin семьи А запросить приглашения и участников семьи Б по их идентификаторам — ответ «не найдено».

**Acceptance Scenarios**:

1. **Given** две семьи, **When** admin семьи А обращается через API к приглашениям и участникам семьи Б, **Then** ответ «не найдено»; данные не раскрыты (AC-9, D-01, N-SEC-02).
2. **Given** две семьи, **When** admin семьи А пытается отозвать приглашение семьи Б или выпустить ссылку сброса для участника семьи Б, **Then** ответ «не найдено»; приглашение действует, ссылка сброса не выпущена (AC-9).

---

### Edge Cases

- Регистрация или принятие приглашения с email существующего аккаунта: явный отказ «email уже зарегистрирован»; аккаунт не создан, приглашение остаётся действующим (FR-035).
- Приглашение истекло или использовано: оно исчезает из списка действующих приглашений (FR-036).
- Двое одновременно регистрируются по одной ссылке приглашения: аккаунт получает один, второй видит отказ как при использованной ссылке.
- Ссылка приглашения или сброса с несуществующим или повреждённым токеном: тот же отказ, что для истёкшей.
- admin выпускает несколько приглашений подряд: все действуют независимо.
- admin выпускает ссылку сброса для самого себя: разрешено.
- Единственный admin забыл пароль и не вошёл: самостоятельного восстановления нет до F10 (см. Assumptions).
- Email в разном регистре (`Anna@x.com`, `anna@x.com`) — один и тот же аккаунт.
- Превышение лимита регистраций с одного адреса: отказ как превышение лимита.
- Пользователь меняет пароль по ссылке сброса, будучи вошедшим на другом устройстве: та сессия завершается.

## Requirements _(mandatory)_

### Functional Requirements

**Регистрация и семья**

- **FR-001**: Система ДОЛЖНА позволять человеку без аккаунта зарегистрироваться, указав email, пароль, имя и название семьи (R-AUTH-01).
- **FR-002**: Когда регистрация без приглашения завершена, система ДОЛЖНА создать аккаунт, семью и взрослый профиль, назначить роль admin и начать сессию (R-AUTH-01, AC-1).
- **FR-003**: Система НЕ ДОЛЖНА позволять регистрацию без приглашения иначе, чем с созданием новой семьи (R-AUTH-01).
- **FR-004**: Система ДОЛЖНА принимать пароль длиной ≥ 10 символов без требований к составу и отклонять более короткий (R-AUTH-10).
- **FR-005**: Система ДОЛЖНА считать email уникальным без учёта регистра.

**Приглашения**

- **FR-006**: Когда admin создаёт приглашение, система ДОЛЖНА выдать одноразовую ссылку со сроком 7 дней (R-AUTH-02, AC-2).
- **FR-007**: Когда человек открывает действующее приглашение и задаёт email, пароль и имя, система ДОЛЖНА создать аккаунт с ролью member и взрослый профиль в семье приглашения и начать сессию (R-AUTH-03, AC-3).
- **FR-008**: Когда приглашение принято, система ДОЛЖНА сделать его ссылку недействительной (R-AUTH-02, AC-3).
- **FR-009**: Если приглашение истекло, использовано, отозвано или не существует, то система ДОЛЖНА отказать, не создавать аккаунт и показать подсказку запросить новое у admin (R-AUTH-04, AC-4).
- **FR-010**: Если приглашение открывает пользователь, уже состоящий в семье, то система ДОЛЖНА отказать (R-AUTH-05).
- **FR-011**: Система ДОЛЖНА позволять admin отозвать неиспользованное приглашение своей семьи; отозванная ссылка перестаёт работать сразу (R-AUTH-06, N-SEC-06).
- **FR-012**: Если приглашение создаёт или отзывает member, то система ДОЛЖНА отказать как «нет прав» — в интерфейсе и в API (AC-5).
- **FR-013**: Система НЕ ДОЛЖНА привязывать приглашение к email: email задаёт приглашённый при принятии (R-AUTH-03).

**Вход, выход, сессии**

- **FR-014**: Система ДОЛЖНА позволять пользователю войти по email и паролю и выйти (R-AUTH-07, AC-6).
- **FR-015**: Система ДОЛЖНА держать сессию 30 дней с момента последней активности (R-AUTH-07).
- **FR-016**: Когда пользователь выходит, система ДОЛЖНА завершить текущую сессию; защищённые страницы и данные становятся недоступны (AC-6).
- **FR-017**: Если пользователь не вошёл, то система ДОЛЖНА отказывать в доступе к защищённым страницам и данным.
- **FR-018**: Если вход неуспешен, то система ДОЛЖНА отвечать одинаково для неверного пароля и несуществующего email (N-SEC-07, AC-7).
- **FR-019**: Система ДОЛЖНА ограничивать вход: 5 попыток в минуту на пару «адрес + email»; следующая отклоняется как превышение лимита без раскрытия существования аккаунта (N-SEC-07, AC-7).
- **FR-020**: Система ДОЛЖНА ограничивать регистрацию по приглашению: 10 в час на адрес (`nfr.md`, Rate limit).

**Сброс пароля**

- **FR-021**: Система ДОЛЖНА позволять admin выпустить для участника своей семьи одноразовую ссылку сброса пароля со сроком 24 часа (R-AUTH-08).
- **FR-022**: Когда участник задаёт новый пароль по ссылке сброса, система ДОЛЖНА сменить пароль, завершить все сессии участника и сделать ссылку недействительной (R-AUTH-08, AC-8).
- **FR-023**: Если ссылку сброса выпускает member, то система ДОЛЖНА отказать как «нет прав».
- **FR-024**: Когда для участника выпускается новая ссылка сброса, система ДОЛЖНА сделать предыдущую недействительной.
- **FR-025**: Если ссылка сброса истекла, использована или не существует, то система ДОЛЖНА отказать и не менять пароль.

**Профиль**

- **FR-026**: Система ДОЛЖНА создавать ровно один взрослый профиль на аккаунт при вступлении в семью (R-AUTH-03, D-06).
- **FR-027**: Система ДОЛЖНА позволять пользователю изменить своё отображаемое имя; пустое имя отклоняется (R-AUTH-09).
- **FR-028**: Система ДОЛЖНА позволять пользователю выбрать язык интерфейса `ru` или `en` и хранить выбор в профиле (R-AUTH-09, AC-10).
- **FR-029**: Пока пользователь не вошёл, система ДОЛЖНА показывать интерфейс на языке браузера, если это `ru` или `en`, иначе на `en` (N-UX-04).
- **FR-030**: Система ДОЛЖНА показывать участнику список участников его семьи: имя и роль.

**Изоляция и приватность**

- **FR-031**: Если пользователь обращается к приглашениям или участникам другой семьи, то система ДОЛЖНА отвечать «не найдено» и не раскрывать данные (D-01, N-SEC-02, AC-9).
- **FR-032**: Система НЕ ДОЛЖНА записывать в логи пароли, токены ссылок, cookie и email (N-PRV-03).
- **FR-033**: Система ДОЛЖНА отклонять изменяющие запросы с чужого источника (N-SEC-13).
- **FR-034**: Все строки интерфейса фичи ДОЛЖНЫ существовать в `ru` и `en` (N-UX-04).

**Решения по уточнениям**

- **FR-035**: Если при регистрации или принятии приглашения указан email существующего аккаунта, то система ДОЛЖНА отказать с сообщением «email уже зарегистрирован» и не создавать аккаунт; приглашение остаётся действующим (✅ Q1 → А).
- **FR-036**: Система ДОЛЖНА показывать admin список действующих приглашений его семьи: дата создания, срок действия, действие «отозвать». Использованные, отозванные и истёкшие приглашения в список не входят (✅ Q2 → А).
- **FR-037**: Система НЕ ДОЛЖНА показывать список приглашений member (`permissions.md`, «Семья»).
- **FR-038**: Система ДОЛЖНА показывать ссылку приглашения только в момент создания; в списке ссылка не отображается.

### Key Entities _(include if feature involves data)_

- **Аккаунт**: тот, кто входит. Email (уникален), пароль. Связан с одним взрослым профилем.
- **Семья**: группа участников. Название. Все данные фичи принадлежат одной семье (D-01).
- **Участие**: связь аккаунта с семьёй и роль: admin или member. В F1 аккаунт состоит ровно в одной семье.
- **Профиль**: член семьи. В F1 — только взрослый: связан с аккаунтом. Отображаемое имя, язык интерфейса.
- **Приглашение**: одноразовое право вступить в семью как member. Семья, срок 7 дней, состояние: действует, использовано, отозвано, истекло.
- **Ссылка сброса пароля**: одноразовое право задать новый пароль участнику. Участник, срок 24 часа, состояние: действует, использована, заменена, истекла.
- **Сессия**: вход аккаунта на устройстве. Срок 30 дней от последней активности.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: Новый пользователь создаёт семью и попадает в приложение за ≤ 2 минуты.
- **SC-002**: Приглашённый проходит путь от открытия ссылки до входа в семью за ≤ 2 минуты, без помощи admin.
- **SC-003**: admin получает ссылку приглашения за ≤ 3 действия с главного экрана.
- **SC-004**: 100% попыток member создать или отозвать приглашение и выпустить ссылку сброса отклоняются.
- **SC-005**: 100% обращений к приглашениям и участникам чужой семьи получают ответ «не найдено».
- **SC-006**: 0 случаев, когда использованная, отозванная или истёкшая ссылка даёт доступ.
- **SC-007**: После сброса пароля 100% прежних сессий участника недействительны при следующем обращении.
- **SC-008**: Ответы на неуспешный вход для существующего и несуществующего email неразличимы по тексту и коду.
- **SC-009**: Все экраны фичи работают при ширине 360 px и доступны на `ru` и `en` без непереведённых строк.
- **SC-010**: Вход, регистрация и принятие приглашения отвечают за ≤ 1 секунду для 95% попыток при 50 одновременных пользователях.
- **SC-011**: admin отзывает любое действующее приглашение за ≤ 3 действия с главного экрана.

## Assumptions

- В объём не входят: детские профили (F8); смена ролей, удаление участников, история приглашений (F7); вход через Google (F13); email-доставка приглашений и сброса (F10); несколько семей на аккаунт (F12).
- Ссылки приглашения и сброса admin передаёт сам, вне приложения: email-доставки нет до F10.
- Подтверждение email не требуется (ADR-003).
- FR-035 раскрывает существование аккаунта при регистрации: N-SEC-07 в редакции от 2026-11-14 это допускает (Q-20). Защита от перебора — лимит регистраций (FR-020).
- Список действующих приглашений (FR-036) перенесён в F1 из F7: без него R-AUTH-06 невыполним.
- Смена собственного пароля и email вошедшим пользователем в объём не входит: бриф их не называет.
- ⚠️ Единственный admin, забывший пароль и не имеющий активной сессии, не восстанавливает доступ средствами приложения до F10; восстановление — вручную оператором.
- В F1 в семье один admin — её создатель: смена ролей — F7.
- Список участников (FR-030) — минимальный, только чтение: он нужен admin для выбора участника при сбросе пароля. Управление участниками — F7.
- Лимиты регистрации, приглашений и выпуска ссылок сброса — `docs/nfr.md`, Rate limit.
- Коды ответов из брифа (AC-5, AC-7, AC-9) фиксируются в контракте на шаге plan; здесь они описаны как исходы: «нет прав», «превышение лимита», «не найдено».
- Механизм аутентификации и хранения сессий задан ADR-003 и в спеке не описывается.
- Зависимости: фаза 2 и локальная часть фазы 3 завершены (монорепо, Postgres, миграции, CI, e2e, i18n-каркас).
