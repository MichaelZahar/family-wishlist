## ADR-001. Технический стек

**Статус:** принят · 2026-11-03

**Контекст.** Боевое веб-приложение: сервер на Node.js, клиент на React + TypeScript. Разработка агентами в Claude Code по SDD; FE- и BE-агенты работают параллельно → нужен явный контракт и минимум шагов, которые агент может забыть.

**Решение:**

| Слой | Выбор |
| --- | --- |
| Репозиторий | Монорепо, pnpm workspaces: `apps/api`, `apps/web`, `packages/shared` |
| Runtime | Node.js 26 LTS, TypeScript (ESM); pnpm ставится через `npm install -g pnpm` (Corepack не входит в Node ≥ 25) |
| API | Fastify + zod type provider |
| Контракт | zod-схемы в `packages/shared` → типы, валидация, OpenAPI |
| БД | PostgreSQL |
| ORM | Drizzle ORM + drizzle-kit (миграции), drizzle-zod |
| Frontend | React + Vite + TypeScript, TanStack Query, React Router |
| i18n | i18next + react-i18next; локали `ru`, `en` (N-UX-04) |
| Тесты | Vitest, inject/Supertest для API, Playwright для e2e |
| Качество | ESLint, Prettier, `tsc --noEmit`, husky + lint-staged |
| CI | GitHub Actions |

**Рассмотренные альтернативы:**

- **Prisma.** Отклонена: отдельный DSL и кодогенерация удлиняют цепочку «схема → контракт». Drizzle: схема на TS, drizzle-zod без генерации, SQL-подобные запросы проще ревьюить.
- **Express.** Нет валидации по схемам, инкапсуляции плагинов, структурированного логгера.
- **NestJS.** Избыточен для масштаба проекта.
- **MongoDB.** Данные сильно связаны; правила видимости — JOIN'ы и ограничения целостности. Гибкие атрибуты → `jsonb`.
- **Next.js.** SSR и SEO не нужны; отдельный Fastify даёт явную границу API.

**Последствия:**

- Версия Node закрепляется в `.nvmrc`, `package.json#engines`, CI `setup-node` и базовом Docker-образе. Node 26 LTS поддерживается до апреля 2029; Node 22 — только до апреля 2027.
- Источник истины: данные — Drizzle-схема; API — zod-схемы в `packages/shared`.
- Контракт меняет только агент `architect`.
- Нет шага кодогенерации ORM.

## ADR-002. Хостинг

**Статус:** принят · 2026-11-03

**Контекст.** Прод с первых недель (walking skeleton). Нагрузка семейная, бюджет минимальный, холодные старты нежелательны.

**Решение.** Railway: один сервис отдаёт API и собранный React; PostgreSQL в том же проекте. Деплой автоматически из `main` после зелёного CI.

**Рассмотренные альтернативы:**

- **Render Free + Neon.** $0, но холодные старты и два провайдера.
- **Render Starter + Render Postgres.** Фиксированная цена, managed-бэкапы, но дороже.
- **Heroku.** Нет бесплатного тарифа, ничего не добавляет к Render.
- **Fly.io.** Нет бесплатного тарифа для новых аккаунтов; edge не нужен.
- **Раздельный хостинг фронта и API.** Cookie на разных доменах → CORS и SameSite=None. Один домен проще и безопаснее.

**Последствия:**

- Оплата по потреблению, ~$5/мес; лимит расходов в Railway.
- Бэкапы Postgres на нас: ежедневный `pg_dump` во внешнее хранилище, проверка восстановления в фазе hardening.
- Конфигурация через env (`DATABASE_URL`, auth secret, `APP_URL`) + Dockerfile → переезд без правок кода.
- Миграции — отдельным шагом перед стартом сервера.

## ADR-003. Аутентификация и сессии

**Статус:** принят · 2026-11-03

**Контекст.** Роли admin/member в семье, приглашения, cookie-сессии на одном домене, детские профили без логина. Security-критичный код не пишем агентами с нуля.

**Решение.** Better Auth внутри Fastify-сервера, данные в нашей Postgres через Drizzle-адаптер.

| Вопрос | Решение |
| --- | --- |
| Библиотека | Better Auth, Drizzle-адаптер, таблицы auth в общей схеме и миграциях |
| Семья и роли | Плагин `organization`: семья = организация, роли admin/member, приглашения; активная семья в сессии |
| Сессии | В БД; cookie `httpOnly` + `Secure` + `SameSite=Lax`; 30 дней, скользящее продление |
| Вход (MVP) | Email + пароль |
| Вход через Google | Could (PRD F13), OAuth-провайдер Better Auth |
| Приглашения | Ссылка с токеном, 7 дней; admin отправляет вручную |
| Сброс пароля | MVP: ссылку генерирует admin. С email-уведомлениями (PRD F10) — самостоятельно |
| Подтверждение email | Не требуется в MVP |
| Защита | Rate limit на вход, регистрацию, приглашения; Origin + SameSite против CSRF |
| Проверка прав | Модуль `authz` в API; тесты по матрице прав |

**User и Profile:**

- `User` — тот, кто логинится (таблицы Better Auth).
- `Profile` — член семьи, владелец желаний. Взрослый связан с `User`; детский: `user_id = null`, задан `managed_by_profile_id`.
- Желания, вишлисты и брони привязаны к `Profile`.

**Рассмотренные альтернативы:**

- **Своя реализация.** Много security-кода от агентов.
- **Clerk, Auth0, Supabase Auth.** Vendor lock-in, лимиты, данные вне нашей БД.
- **JWT в localStorage.** Уязвим к XSS, сложный отзыв.

**Последствия:**

- Агенты пишут правила доступа, а не криптографию.
- Флаги плагинов сверяем с исходниками Better Auth.
- `security-reviewer` проверяет каждую фичу, затрагивающую `authz`.

## ADR-004. Мультиарендность

**Статус:** принят · 2026-11-03

**Контекст.** UI MVP — одна семья; позже несколько семей на аккаунт (PRD F12).

**Решение.** Каждая доменная таблица содержит `family_id`. Фильтр по активной семье применяется централизованно в слое доступа к данным и `authz`.

**Рассмотренные альтернативы:**

- **Одна семья на инстанс.** F12 потребует миграции всех таблиц.
- **Схема/БД на семью.** Избыточно.
- **Row-Level Security.** Усложняет пулинг и отладку; можно добавить позже вторым рубежом.

**Последствия:**

- `family_id` = id организации Better Auth.
- Тест «данные другой семьи недоступны» на каждый эндпоинт (IDOR).

## ADR-006. Локальное окружение

**Статус:** принят · 2026-11-12

**Контекст.** Нужен быстрый цикл разработки на Mac для человека и агентов, паритет с продом по БД и параллельная работа агентов в нескольких git worktree.

**Решение:**

| Компонент | Как запущен |
| --- | --- |
| Контейнерная среда | Docker Desktop for Mac |
| Postgres | Docker Compose, `postgres:17` (версия = прод) |
| API (Fastify) | Нативно, `tsx watch` |
| Web (Vite) | Нативно, dev-сервер с HMR; прокси `/api` → API (один origin, как в проде) |
| Тесты | Vitest против отдельной тестовой БД; Playwright локально |
| Worktree | Один контейнер Postgres; БД `wishlist_<branch>` и порты API/Vite — на каждый worktree, через `.env.local` |

Команды: `pnpm db:up`, `pnpm db:migrate`, `pnpm db:seed`, `pnpm dev`, `pnpm test`, `pnpm e2e`, `pnpm wt:new <feature>`.

**Контуры проверки:** локально (секунды) → CI на PR с Postgres-сервисом (минуты) → прод на Railway после merge. Preview-окружения Railway на PR — TBD, фаза 3.

**Рассмотренные альтернативы:**

- **API и web в контейнерах.** Медленный watch из-за файловой синхронизации на Mac, сложнее отладка. Контейнер API — только для прода (Dockerfile, ADR-002).
- **Проверка через деплой.** Цикл в минуты вместо секунд.
- **OrbStack, Colima.** Легче Docker Desktop; выбран Docker Desktop как знакомый инструмент.
- **Postgres через Homebrew.** Нет изоляции и паритета версий, сложнее сброс.

**Последствия:**

- Агент НЕ ДОЛЖЕН запускать миграции и тесты против чужой БД worktree.
- Сброс окружения: `docker compose down -v` + `pnpm db:up && pnpm db:migrate && pnpm db:seed`.
- Dev-контейнер для автономных агентов — TBD, фаза 4.

## ADR-005. Доступ к вишлисту по ссылке

**Статус:** принят · 2026-11-12

**Контекст.** Гость без аккаунта открывает вишлист по ссылке, видит «занято» и бронирует с именем (R-LST-04…05, R-RES-04…05). Ссылку можно отозвать, и отзыв действует сразу (N-SEC-06). Токен в URL может утечь через Referer, логи, историю браузера.

**Решение:**

| Вопрос | Решение |
| --- | --- |
| URL | `https://<app>/s/<token>` |
| Токен | 32 случайных байта (256 бит), base64url. В `ShareLink.token_hash` — SHA-256 (D-08). Поиск по хешу |
| Активные ссылки | ≤ 1 на вишлист. «Новая ссылка» = отзыв старой + выпуск новой |
| Сессия гостя | Без cookie и без сессии: токен передаётся в каждом запросе `/api/public/s/:token/...`, проверяется каждый раз → отзыв мгновенный |
| API | Отдельный префикс `/api/public/*`: не читает cookie сессии, свои rate limits (N-SEC-07), свои DTO |
| Субъект `authz` | `{ kind: "guest", shareLinkId, wishlistId }`. Права — колонка «Гость» в `permissions.md` |
| Что видит гость | Название вишлиста, отображаемое имя владельца, желания, «занято» без имени (R-RES-05). Ничего больше о семье (N-PRV-05) |
| Гостевая бронь | `guest_name` 1–50 символов. В ответ — токен брони (256 бит), в БД хеш (`guest_token_hash`). Клиент хранит его в `localStorage` → гость может отменить бронь из того же браузера. Токен потерян → отменяет только admin |
| Защита токена | На `/s/*` и `/api/public/*`: `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex`, `Cache-Control: no-store`. Путь с токеном маскируется в логах и Sentry (N-PRV-03) |
| Архив | Когда вишлист уходит в архив (R-HIS-01), ссылка отзывается автоматически |
| Пользователь семьи по ссылке | Видит гостевой интерфейс + подсказку «открыть в приложении»; права гостя, не члена семьи |

**Рассмотренные альтернативы:**

- **Аккаунты для гостей.** Non-goal PRD.
- **Magic link по email.** Нужен email-сервис (F10) и лишний шаг для гостя.
- **Подписанный токен (JWT) без записи в БД.** Нельзя отозвать мгновенно.
- **Cookie-сессия гостя после первого открытия.** Сложнее отзыв и CSRF-модель; выигрыш небольшой.

**Последствия:**

- Каждый публичный запрос — поиск по хешу токена; индекс на `ShareLink.token_hash`.
- `authz` получает третий тип субъекта (пользователь, управляющий, гость); тесты колонки «Гость» обязательны (N-SEC-01).
- Логирование и Sentry ДОЛЖНЫ иметь фильтр, маскирующий токены в путях.
