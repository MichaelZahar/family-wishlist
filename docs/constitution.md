# Family Wishlist — конституция проекта

Версия 1.0.0 · 2026-11-12. Обязательна для людей и агентов. Вход для Spec Kit (`.specify/memory/constitution.md` — копия этого файла).
Источники: `prd.md` (R-…), `domain-model.md` (D-…), `permissions.md`, `nfr.md` (N-…), `adr.md` (ADR-…), `style-guide.md`.

## Принципы

### I. Спека раньше кода

- Код пишется только по утверждённым spec → plan → tasks.
- Изменение поведения ДОЛЖНО менять спеку в том же PR.
- Спека противоречит PRD, ADR или NFR → работа останавливается, вопрос поднимается человеку.

### II. Трассируемость

- Каждое требование спеки, задача и тест ссылаются на ID: `R-…`, `D-…`, `N-…`, `ADR-…`.
- Код без связанного требования НЕ ДОЛЖЕН появляться.

### III. Тесты раньше реализации

- Acceptance criteria → тесты → реализация. Новый тест сначала падает.
- Каждая ячейка `permissions.md` и каждый инвариант D-… покрыты тестом.
- Тест НЕ ДОЛЖЕН ослабляться или удаляться, чтобы пройти; только по решению в спеке.

### IV. Контракт первым

- API-контракт — zod-схемы в `packages/shared` (ADR-001).
- Контракт фиксируется на шаге plan и не меняется во время implement. Менять его может только агент `architect`.

### V. Безопасность и приватность по умолчанию

- Права проверяются только в модуле `authz`; проверки «на месте» в обработчиках ЗАПРЕЩЕНЫ.
- Каждый запрос к данным фильтруется по `family_id` (ADR-004).
- Данные о бронях исключаются на уровне сериализации (N-PRV-01). Утечка брони владельцу — критический баг.
- Собственная криптография ЗАПРЕЩЕНА (ADR-003). Внешние URL загружаются только через SSRF-защищённый клиент (N-SEC-08…11).
- Секреты, токены, email не попадают в код, логи и тестовые снимки.

### VI. Простота

- Решения под масштаб из `nfr.md`, раздел 1. Абстракция «на будущее» без требования ЗАПРЕЩЕНА.
- Новая зависимость — только с обоснованием в plan.
- Архитектурное изменение (стек, хостинг, auth, модель данных) — только через новый ADR.

### VII. Границы модулей

| Зона | Путь | Владелец |
| --- | --- | --- |
| API | `apps/api` | `backend-dev` |
| Web | `apps/web` | `frontend-dev` |
| Контракт | `packages/shared` | `architect` |
| Спеки и документы | `specs/`, `docs/` | `architect` + человек |

Изменение вне своей зоны — только через задачу владельца зоны.

### VIII. Интерфейс

- Все строки UI — через i18n-ключи (N-UX-04), локали `ru` и `en` обновляются вместе.
- Mobile-first, от 360 px (N-UX-01).

### IX. Документация

- Все документы и описания PR — по `style-guide.md`.
- «Что» — в спеках и PRD, «почему» — в ADR.

## Гейты качества

PR сливается в `main`, только если:

1. CI зелёный: lint, typecheck, unit, API-тесты, build, e2e.
2. Все acceptance criteria спеки проверены (`/verify-spec`).
3. Ревью `reviewer` пройдено; для изменений в `authz`, auth, публичном API, разборе ссылок — также `security-reviewer`.
4. Человек утвердил spec, plan и PR.

## Definition of Done

- [ ] Требования спеки реализованы и покрыты тестами.
- [ ] Новые ячейки матрицы прав и инварианты покрыты тестами.
- [ ] Строки UI в `ru` и `en`.
- [ ] Миграции обратно совместимы (N-BAK-03).
- [ ] Документы (спека, при необходимости PRD/ADR) обновлены.
- [ ] Запись в `docs/process-log.md`.

## Управление

- Изменение конституции — PR с правкой версии: MAJOR — меняется или удаляется принцип; MINOR — новый принцип; PATCH — уточнение формулировок.
- Предложения по изменению собираются в ретро после каждой фичи.
- При конфликте приоритет: конституция → ADR → NFR → PRD → спека фичи.
