# Style guide документации

Применяется ко всем документам проекта: PRD, ADR, спеки, планы, `CLAUDE.md`, конституция, PR-описания.
Цель: быстро читать человеку, дёшево читать агенту, однозначно проверять.

## 1. Базовые правила

| # | Правило | Плохо | Хорошо |
| --- | --- | --- | --- |
| S1 | Одна мысль — одна строка | Абзац из трёх связанных идей | Три пункта списка |
| S2 | Сначала факт. Причина — только если неочевидна | «Поскольку важно сохранить сюрприз, владелец не видит брони» | «Владелец не видит брони» |
| S3 | Без вводных и связок | «Важно отметить, что по сути…» | — (удалить) |
| S4 | Утвердительно, в настоящем времени | «Предполагается, что будет возможность…» | «Пользователь может…» |
| S5 | Конкретика вместо оценок | «быстро», «удобно», «много» | «≤ 2 с», «3 клика», «до 50 желаний» |
| S6 | Без повторов. Определение — один раз, дальше ссылка | Пересказ правила в трёх разделах | «см. R-RES-01» |
| S7 | Таблица, если ≥ 3 объекта с общими атрибутами | Три абзаца про роли | Таблица «роль · права · ограничения» |
| S8 | Термины — из глоссария, без синонимов | «желание» / «пожелание» / «позиция» вперемешку | Только «желание» |

**Стоп-слова** (удалять): важно отметить, стоит сказать, по сути, в целом, фактически, как правило, на самом деле, данный, является, осуществлять, в рамках, с точки зрения, а также (в начале фразы), т.е. в середине мысли.

## 2. Требования

- Каждое правило имеет ID: `R-<ОБЛАСТЬ>-<NN>`. Пример: `R-RES-01`.
- Модальность по RFC 2119:

| Слово | Значение |
| --- | --- |
| ДОЛЖЕН / НЕ ДОЛЖЕН | Обязательно. Нарушение = баг |
| СЛЕДУЕТ / НЕ СЛЕДУЕТ | Рекомендовано; отклонение требует причины |
| МОЖЕТ | Опционально |

- Поведение — в формате EARS:

| Тип | Шаблон |
| --- | --- |
| Всегда | Система ДОЛЖНА <поведение> |
| Событие | Когда <событие>, система ДОЛЖНА <реакция> |
| Состояние | Пока <состояние>, система ДОЛЖНА <поведение> |
| Нежелательное | Если <ошибка/условие>, то система ДОЛЖНА <реакция> |
| Опция | Где включено <фича>, система ДОЛЖНА <поведение> |

- Acceptance criteria — Given / When / Then, по одному сценарию на блок.

Пример:
> **R-RES-01.** Система НЕ ДОЛЖНА показывать владельцу желания факт, автора и время брони.
> **R-RES-02.** Когда дарящий бронирует желание, система ДОЛЖНА показать «занято» всем остальным получателям вишлистов с этим желанием.

## 3. Структура документов

- Шаблон с фиксированными слотами. Пустой слот — `—` или `TBD: <вопрос>`, не удалять.
- Лимиты:

| Элемент | Лимит |
| --- | --- |
| Раздел «Проблема» / «Контекст» | ≤ 5 строк |
| Описание фичи («Суть») | 1 строка |
| Пункт списка | ≤ 2 строки |
| Абзац | ≤ 3 предложения |

- Шаблон фичи: `ID · Название · Суть · Правила (R-…) · Acceptance criteria · Зависимости · Приоритет`.
- Открытые вопросы — нумерованный список `Q-NN`, у каждого варианты ответа. Закрытый вопрос: `✅ Q-NN → решение`.

## 4. Что куда

| Тип содержания | Где живёт |
| --- | --- |
| Что система делает | PRD, спеки |
| Почему так решили | ADR |
| Рассуждения, варианты, споры | Комментарии, чат, PR-обсуждение |
| Как устроен код | `CLAUDE.md`, README модулей |
| Термины | Глоссарий (раздел PRD) |

## 5. Форматирование

- Заголовки — существительные: «Бронирование», не «Как работает бронирование».
- Жирный — только для терминов при первом определении и ключевых запретов.
- Код, пути, поля, переменные — в `backticks`.
- Без эмодзи, кроме ✅ (решено) и ⚠️ (риск).
- Ссылки на другие документы — путь или ID, не пересказ.

## 6. Проверка перед публикацией

1. Можно ли удалить предложение без потери факта? → удалить.
2. Есть ли стоп-слова? → удалить.
3. Есть ли оценки без чисел? → заменить числом или `TBD`.
4. Повторяется ли определение? → заменить ссылкой.
5. Требование однозначно проверяемо тестом? → если нет, переписать в EARS.

Целевой эффект редактуры: −30–40% объёма без потери фактов.
